02. Architecture & Hierarchy

The Decision Hierarchy: AI Proposes, System Decides

Deterministic rules handle what we already understand; AI is introduced strictly when decisions become ambiguous.

< 1ms Latency 68% of Cases

  • Provides deterministic latency SLA without external AI dependencies.

03. Distributed Systems Engineering

The Hard Part Wasn't AI: Concurrency & Idempotency

In an event-driven payment system, duplicate events are inevitable. Duplicate debits are intolerable.

PILLAR 1: CONCURRENCY COORDINATION

Redis Distributed Locks

Answers: "Who has authorization to work on this payment right now?"
  • Prevents competing recovery workers from executing duplicate retries concurrently.
  • Atomic lock acquisition: SET lock:rec:{payment_id} NX EX 60
  • Automatic TTL expiration eliminates deadlocks if a worker node crashes mid-flight.
  • Safe release via Lua script ensures only the owner token can unlock.
PILLAR 2: DURABLE FINALITY

Database Idempotency Barrier

Answers: "Has this recovery action already occurred or been committed?"
  • Provides relational protection against retried, redelivered, or delayed Kafka events.
  • Deterministic key constraint: UNIQUE(idempotency_key)
  • Pre-execution reservation pattern commits pending record before invoking gateway.
  • Guarantees EXACTLY-ONCE financial mutation across network partitions.
💡 Key Architectural Rule: A lock alone does not guarantee idempotency. Distributed Redis locks handle in-flight race conditions; the database idempotency barrier guarantees historical exactly-once execution forever.
04. Financial Safety & Edge Cases

Dynamic State Inversion & Timeout Ambiguity

Payment recovery is an asynchronous time-travel problem where reality changes while you wait.

EDGE CASE 1

Dynamic State Inversion

Payment succeeds while recovery is waiting in the delayed queue.
1. $T_0$: Attempt #1 fails on primary rail.
2. $T_1$: Recovery orchestrator schedules retry for $T_0 + 60\text{s}$.
3. $T_2$: Customer re-opens checkout and pays successfully via UPI!
4. $T_3$: Recovery worker wakes up to retry original payment.
🛡️ IRO Solution: Authoritative Pre-Execution Revalidation
Before executing, IRO queries the source-of-truth payment state. If status == SUCCESS, recovery is stopped immediately with zero action.
EDGE CASE 2

Gateway Timeout Ambiguity

A timeout does NOT mean the payment failed.
1. Acquirer gateway drops connection after 15,000ms.
2. Did the customer's bank account get debited? Unknown.
3. Did the merchant capture the payment? Unknown.
4. Blind retries cause double debits and severe customer complaints.
🛡️ IRO Solution: Hold for Reconciliation
Classifies timeout as ambiguous in-flight. Case enters a holding state with automated polling against the bank settlement inquiry API before deciding.
05. AI Infrastructure & Operations

AI as Infrastructure: Tiered Routing & L7 Scaling

The goal is not to use more AI. It is to use exactly as much intelligence as the decision requires.

LAYER 1: MODEL ROUTER

What tier should handle this recovery?

Routes simple classifications to lightweight models (5ms, $0.0005/1k tokens), reserving deeper reasoning models (25ms) strictly for complex multi-attempt investigations.

TASK-DRIVEN ROUTING
LAYER 2: L7 ADAPTIVE LOAD BALANCER

Which healthy instance should receive the request?

Continuous health checking (HEALTHY, DEGRADED, DOWN) with least-connections dispatching across specialist worker containers.

INSTANCE LOAD BALANCER
LAYER 3: ZERO-OVERHEAD DETERMINISTIC BYPASS

When should AI be avoided completely?

68% of all recovery traffic bypasses AI entirely. If AI worker pools fail or spike in latency, system gracefully degrades to deterministic rules with zero downtime.

08. Key Takeaways

Core Learnings: Payment Recovery Beyond AI

Payment recovery is fundamentally a systems engineering challenge, and only sometimes an AI challenge.

PILLAR 1

A Reliability Problem

FSM state machines, dead-letter recovery queues, and bounded retry intervals.

PILLAR 2

A Concurrency Problem

Distributed Redis locking (SET NX EX) and durable relational idempotency barriers.

PILLAR 3

A Policy Problem

Deterministic financial policy guards, retry thresholds, and regulatory compliance.

PILLAR 4

A Cost Problem

Right-sized model routing, L7 load balancing, and fast deterministic bypass for 68% of traffic.

PILLAR 5

And Only Sometimes...

An AI problem. Introduced strictly when recovery decisions become ambiguous.
